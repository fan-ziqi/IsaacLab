贡献指南#

参见

本页是 isaaclab-following-coding-style 、 isaaclab-preparing-pr-workflow 和 isaaclab-writing-changelog-fragments 智能体技能的权威依据（ skills/developer/coding-style/ 、 skills/developer/pr-workflow/ 、 skills/developer/changelog-fragments/ ）。共享指导改变时，应更新相关技能的工作流和示例，不要复制规则。参见 智能体技能 。

我们衷心欢迎对项目的贡献，以使框架更加成熟并对大家更加有用。这些贡献可能以以下形式出现:

  • Bug 报告: 如果您发现任何 bug，请在 issue tracker 中报告。

  • 功能请求: 请提出您希望在 discussions 中看到的新功能。

  • 代码贡献: 请提交一个 pull request 。

    • 错误修复

    • 新特性

    • 文档改进

    • 教程和教程改进

我们更倾向于使用 GitHub discussions 来讨论想法、提问、交流和新功能的请求。

请仅使用 issue tracker 来跟踪具有明确范围和清晰交付物的可执行任务。这些任务可以是修复 bug、新功能或一般更新。

贡献代码#

注意

请参阅 Google Style Guide 以了解编码风格，然后再为代码库做贡献。在编码风格部分，我们概述了代码库中遵循的与风格指南的具体偏差。

我们使用 GitHub 进行代码托管。请按照以下步骤贡献代码:

  1. 在 issue tracker 中创建一个问题，讨论您希望进行的更改或添加内容。这有助于我们避免重复工作，并确保这些更改与项目的路线图保持一致。

  2. Fork 仓库。

  3. 创建一个新分支用于您的更改。

  4. 进行更改并提交它们。

  5. 将您的更改推送到您的 fork。

  6. 向 develop 分支 提交 PR。

  7. 确保对拉取请求模板执行所有检查。

在发送拉取请求之后，维护者将审查你的代码并提供反馈。

确保代码格式正确、文档完整，并按 单元测试 和 工具 所述，运行相关测试和必需的 CI 检查。

小技巧

保持拉取请求尽可能小是很重要的。这使得维护者更容易审查你的代码。如果你正在进行多个更改，请发送多个拉取请求。大型拉取请求很难审查，并且可能需要很长时间才能合并。

关于代码风格和测试的更多细节可以在 代码风格 和 单元测试 部分找到。

贡献文档#

为文档贡献的方式与为代码库贡献一样简单。所有文档的源文件都位于 IsaacLab/docs 目录中。文档使用 reStructuredText 格式编写。

我们使用 Sphinx 和 Book Theme 来维护文档。

API 的 [source] 链接在 GitHub 上打开实现，使用发布文档对应的分支或标签；当前检出目录的构建默认为 develop 。我们不生成本地 Python 源码页，因此查看实现需要联网。

发送文档的拉取请求与发送代码库的拉取请求相同。请按照 贡献代码 部分中提到的步骤进行操作。

文档媒体中，只有较小的 .jpg 文件应直接提交到 Isaac Lab 仓库。较大的图片、视频、动画等媒体，应上传到外部托管位置，再从文档链接或嵌入。

小心

构建文档前，先安装 uv 。构建命令将包含文档依赖的 dev 可选依赖组同步到仓库的 .venv 。

根据修改影响的行为，选择文档验证方式：

  • 渲染文档不受影响时，跳过 Sphinx，包括单独修改 AGENTS.md 或 skills/ 的情况，改为运行相关代码或技能检查。

  • 编辑文档页时，使用增量 HTML 预览。

  • 修改 API 签名、文档字符串、Sphinx 配置或扩展，以及主题时，使用全新构建；Sphinx 缓存不能可靠检测 Python 源码变更。

  • 提交 PR 前，对最终影响文档的修改执行一次全新构建，并确保没有警告。只有后续又有相关修改或构建失败时，才需要重复。CI 也会执行全新构建。

增量 HTML 预览在 Linux 和 Windows 上均从仓库根目录运行：

uv run --extra dev --directory docs python -m sphinx -W --keep-going -j auto . _build/incremental

有 Make 的系统可使用等价命令：

uv run --extra dev make -C docs incremental-docs

打开 docs/_build/incremental/index.html 查看预览。后续运行复用缓存，将新警告视为错误，但可能遗漏旧警告或保留已删除页面。最终验证应使用全新构建；不要向同一输出目录并发构建。

最终全新构建从仓库根目录运行以下命令。它安装文档包，并构建当前版本：

uv run --extra dev isaaclab --docs

文档生成于 docs/_build/current 。在浏览器打开 docs/_build/current/index.html 查看。每次构建都会清空当前 HTML 输出和 Sphinx 缓存，避免保留已删除页面或缓存中的警告。

贡献资产#

大型资产文件不应直接加入 Isaac Lab 仓库，应托管在独立仓库，再从相关文档链接过去。

请查看 Isaac Sim 资产 以了解当前可用资源的更多信息。

注意

我们目前正在研究一种更好的方式来贡献资产。一旦我们有了解决方案，我们将更新此部分。在此期间，请按照下面提到的步骤进行操作。

要托管您自己的资源，当前的解决方案是:

  1. 创建一个单独的存储库用于资产，并将其添加到那里

  2. 确保资产已获得使用和分发的许可

  3. 在仓库的 README 文件中包含资产的图片

  4. 发送一个包含仓库链接的拉取请求

我们随后会验证资产及其许可，并确定集成方式。如有疑问，请在仓库提交 issue。

维护包的变更日志与版本#

每个纳入发布管理的包，在 docs/CHANGELOG.rst 中维护变更日志，在 pyproject.toml 中维护版本。

变更日志按时间顺序整理各包版本的重要变更。

备注

CI 每晚根据各 PR 的 towncrier 片段文件 ，生成 CHANGELOG.rst 和 pyproject.toml 中的包版本；贡献者不直接编辑二者。对于 PR 修改的每个 source/<pkg>/ 包（不计 changelog.d/ ），在 source/<pkg>/changelog.d/ 下添加片段：

  • <slug>.<type>.rst ：每种条目类型一个文件， <type> 为 added 、 changed 、 deprecated 、 removed 或 fixed ；文件包含对应章节的列表条目。

  • <slug>.minor 或 <slug>.major ：空文件，将版本升级级别从补丁级提高到次版本级（新增公共 API）或主版本级（不兼容变更）。

  • <slug>.skip ：空文件，不生成条目也不升级版本，适用于只修改 CI、文档或测试的 PR。

<slug> 可使用任意简短、唯一的名称；建议默认采用分支名，并将 / 替换为 - 。同一批次中，该包采用最高升级级别。CI 按 语义化版本 升级 pyproject.toml 中的包版本。

变更日志使用 reStructuredText 格式，帮助用户和贡献者准确了解各包版本之间的重要变更。每个纳入发布管理的包都 必须 提供变更日志。

编写各片段时，遵循以下指南：

  • 各片段的 <type> 指定其条目所属的变更日志章节。

    • added ：新增功能。

    • changed ：已有功能的变更。

    • deprecated ：即将移除的功能。

    • removed ：已移除的功能。

    • fixed ：错误修复。

  • 每项变更使用 * 列表项描述，续行缩进。

  • 不兼容变更以 Breaking: 开头；对于调用方需要适配的弃用、变更或移除行为，提供迁移说明。

  • 项目要点采用 过去时 编写。

    • 这意味着这个变化被描述为已经发生过。

    • 项目要简明扼要，直奔主题。不应冗长。

    • 项目符号应当包括变更的原因，如果适用。

小技巧

有疑问时，请检查现有的 changelog 文件中的样式，并遵循相同的样式。

例如， source/isaaclab/changelog.d/fix-partial-reset.fixed.rst ：

* Fixed contact sensor reset behavior when only a subset of environments was reset.

编码风格#

我们遵循 Google Style Guides 作为代码库的规范。对于 Python 代码，遵循 PEP 指南。最重要的包括 PEP-8 用于代码注释和布局， PEP-484 和 PEP-585 用于类型提示。

对于文档，我们采用 Google Style Guide 来编写 docstring。我们使用 Sphinx 来生成文档。请确保您的代码有良好的文档说明并遵循指南。

重构与 API 设计#

采用能解决问题的最小修改。修改接口前，阅读周边代码、调用方、测试和文档。新增代码或整理现有实现时，遵循以下规则：

  • 除非修改明确要求，否则保留可观察行为。除返回值外，还要检查顺序、形状、dtype、设备、输入修改和失败行为。移除或重命名公共 API，需要弃用过程和迁移方式。

  • 无状态计算与转换优先采用函数式方式：使用输入、输出明确的普通函数，将副作用放在清晰边界。需要持有实质状态或资源、在生命周期内维护不变量，或实现架构要求的接口时，使用类。避免仅为归组静态方法、包装单个操作或转发另一对象调用而建立类。简化现有设计时，保留既有公共约定。

  • 引入辅助函数、配置选项或抽象前，先复用现有机制。共享逻辑约定相同时再提取；除非调用方需要公共 API，否则辅助函数应保持私有。直接控制流和提前返回能减少不必要嵌套时，应优先使用。

  • 如果辅助函数只增加跳转层级，简单表达式和操作应直接写在调用处。不要仅为给显而易见的操作改名而提取单行函数。只有能消除实质重复，或为完整、非简单操作提供有用名称时，才引入辅助函数；收益应超过理解调用方时跳到另一处定义的成本。

  • 优先直接访问和赋值属性（ obj.value 、 obj.value = value ）。只有需要动态访问，例如属性名在运行时确定时，才使用 getattr 、 setattr 。不要将它们用于已知属性，也不要用默认值掩盖缺失的必需属性；可选字段应在接口中明确表达。

  • 每项状态和验证都应只有一个负责方。使用方应遵循其约定，而不是自行修补结果或维护重复状态。只有派生值的生命周期和失效方式明确时才缓存，不要暴露可能被调用方意外修改的可变缓存结果。

  • 在共享分派边界选择后端。使用既有类型、配置和能力约定，不要根据类名字符串推断行为。

  • 分开物理与渲染职责，并在最终构建完成前解决构建要求。几何归属见 场景数据提供器 ，后端集成见 添加物理后端 。

  • 优先使用项目已有依赖和标准库。不要为假设中的未来用途添加依赖或兼容层。

数组操作与运行开销#

检查每步、每次重置或每个环境执行的代码中的分配、复制、同步和重复计算。单个环境中很小的开销，在大批次中可能占主要部分。

  • 支持切片的 API 应保留切片，只有使用方要求具体索引时才生成索引数组，并尽量复用缓存的设备索引。保留选择器的顺序和设备约定。

  • 直接按所需值、dtype 和设备分配数组。优先使用 torch.full 、 wp.full ，而不是通过 Python 列表填充、对临时数组做算术，或经由另一库来回转换。

  • 只有检查布局与归属要求后，才移除多余复制和 contiguous() 调用。除非 API 明确承诺原地操作，否则不要修改调用方所有的输入。

  • 支持时使用批量操作。在热点路径中，避免通过 Python 循环遍历环境，以及不必要的主机与设备传输，或会同步设备的标量读取。

  • 生命周期允许时，开销较大的可选缓冲区可在首次使用时分配。还要考虑计算图捕获：如果分配器有此要求，必需分配必须在捕获前完成。

命名与文档#

  • 函数、方法和命令行参数使用 snake_case 。通过一致的前缀使相关公共符号易于发现，并沿用已有 API 词汇。

  • 可行时使用具体类型、 list[str] 等内置集合注解，以及表示可选值的 X | None 。参数和返回类型放在签名中，不在文档字符串重复。

  • 公共 API 使用 Google 风格文档字符串。物理单位直接写在描述中，例如 Particle positions [m], shape [N, 3] 。混合关节量使用 [m or rad, depending on joint type] 。适用时说明坐标系和数组形状；索引、计数和标志不需要物理单位。

  • 注释保持简短、有选择性。解释代码本身无法说明的意图、不明显约束或边界情况，不要逐步叙述实现，也不要重复表达式作用。欢迎有助于组织文件的可读性注释、章节标记和标题。

  • 代码注释描述当前约定。迁移说明和旧行为描述应放在公共迁移文档或变更日志中，不要在实现内留下重构历史。只有历史背景能解释仍影响正确性的约束时，才保留它。

  • API 改变时同步更新公共文档，并根据实现核实技术说明。

代码结构#

我们遵循特定的代码库结构。这有助于维护代码库并使其更易于理解。

在配置的长度限制内，短表达式写在一行；长表达式在有意义的边界换行。循环头只关注迭代，复杂嵌套记录在循环体内解包。优先使用描述性名称，避免新缩写。通过 * / ** 复用匹配的序列或映射，不要解包后重建；也不要仅为缩短代码而引入打包容器或反射赋值。

在一个 Python 文件中，我们遵循以下结构：

# Imports: These are sorted by the pre-commit hooks.
# Constants
# Functions (public)
# Classes (public)
# _Functions (private)
# _Classes (private)

通过 uv run isaaclab -f ，由 Ruff 排序导入。分组依次为 __future__ 、标准库、第三方包、Omniverse 运行时包、Isaac Lab 包和本地相对导入；具体包分组在 pyproject.toml 中配置，由格式化器应用顺序。同一包内、目标最多需要三个前导点时，使用相对导入，例如 from ...utils import math as math_utils 。更深目标、其他包，以及包含 if __name__ == "__main__": 并作为脚本运行的模块，使用绝对导入。

优先在模块层导入。局部导入适用于将可选后端或仿真器依赖推迟到所选运行路径确实需要时。配置导入应能在仿真器启动前使用，不要重复包已负责的运行时初始化。循环导入可使用 typing.TYPE_CHECKING 处理，详情见 循环导入 。

__init__.py 中的公共导出模块是例外：使用 lazy_export() ，而非传统导入。详情见 延迟加载与模块导出 。

直接向 Warp 核函数传入 ProxyArray 对象。每个自有数组只保留一个代理，不要并行保存 _ta 、 _warp 或 _torch 属性；带时间戳的数组缓存可在 data 中持有代理。只有接收 API 要求时，才显式访问原生数组。

Python 没有私有和公共类和函数的概念。然而，我们遵循用下划线作为私有函数和类前缀的约定。公共函数和类是供用户使用的函数和类。私有函数和类是旨在在该文件内部使用的函数和类。无论函数和类是公共还是私有的，我们都遵循代码的风格指南，并确保代码和文档一致。

确实需要类时，按以下顺序组织成员：

# Constants
# Class variables (public or private): Must have the type hint ClassVar[type]
# Dunder methods, when needed: __init__, __del__
# Representation: __repr__, __str__
# Properties: @property
# Instance methods (public)
# Class methods (public)
# Static methods (public)
# _Instance methods (private)
# _Class methods (private)
# _Static methods (private)

经验法则是类中的函数按照用户期望使用它们的方式排序。例如，如果类包含方法 initialize(), reset(), update(), 和 close(), 然后它们应该按照使用顺序列出。私有函数在类中也适用相同的规则。他们的顺序基于在类内部调用的顺序。

只包含类所需的成员；这一顺序不是要求实现所有方法的清单。持有资源的类，应通过 close() 或上下文管理器提供显式清理。

最小函数示例
# Copyright (c) 2022-2026, The Isaac Lab Project Developers (https://github.com/isaac-sim/IsaacLab/blob/main/CONTRIBUTORS.md).
# All rights reserved.
#
# SPDX-License-Identifier: BSD-3-Clause


def normalize_weights(weights: list[float]) -> list[float]:
    """Scale non-negative weights to sum to one without modifying the input.

    Args:
        weights: Finite, non-negative weights with a positive total.

    Returns:
        Normalized weights in the input order.

    Raises:
        ValueError: If a weight is negative or the total is not positive.
    """
    total = sum(weights)
    if total <= 0 or any(weight < 0 for weight in weights):
        raise ValueError("Weights must be non-negative with a positive total.")
    return [weight / total for weight in weights]

循环导入#

循环导入发生在两个模块相互导入时，这是 Python 中常见的问题。您可以通过遵循在此 StackOverflow post 中概述的最佳实践来防止循环导入。

一般来说，避免循环导入是至关重要的，因为它们可能导致不可预测的行为。

然而，在我们的代码库中，我们在子包级别遇到了循环导入。这种情况是由于我们特定的代码结构所导致的。我们将类或函数及其相应的配置对象组织到不同的文件中。这种分离增强了代码的可读性和可维护性。然而，它可能导致循环导入，因为在许多配置对象中，我们使用属性 class_type 和 func 分别指定类或函数作为默认值。

为解决这一问题，采用两种互补方式：

  1. 可解析字符串 ：将 class_type 和 func 存为基于 {DIR} 的字符串，例如 "{DIR}.sensor:Sensor" ，避免构建配置时导入实现模块。调用或访问需要实现的属性时，通过 ResolvableString 将字符串解析为实际类。触发解析前，先初始化所需运行时。

  2. TYPE_CHECKING 保护 ：在 typing.TYPE_CHECKING 条件下导入实现类，使 IDE 和类型检查器可根据类型注解补全，而不触发运行时导入。

两种方式的完整示例见 可解析字符串 和 延迟加载与模块导出 。

配置操作#

使用 instantiate() 构建配置所选择的实现：

from isaaclab.utils import clone, instantiate, replace, to_dict, update_from_dict, validate

robot_cfg = replace(ROBOT_CFG, prim_path="{ENV_REGEX_NS}/Robot")
other_cfg = clone(robot_cfg)
update_from_dict(other_cfg, {"init_state": {"pos": (1.0, 0.0, 0.0)}})
validate(other_cfg)
settings = to_dict(other_cfg)
robot = instantiate(robot_cfg)
action = instantiate(action_cfg, env)

instantiate 将配置作为构造函数第一个参数，后接额外参数。它不复制配置、不构建嵌套配置，也不缓存实例。资源共享仍由 SimulationContext.get_or_create_backend 负责。

clone 和 replace 返回新配置，保留显式标记为借用的字段； update_from_dict 原地更新现有配置； validate 检查必需字段，并运行嵌套的 validate_config 钩子。新代码优先使用这些函数。现有 cfg.copy() 、 cfg.replace(...) 、 cfg.validate() 、 cfg.to_dict() 、 cfg.from_dict(...) 和 cfg.class_type(cfg, ...) 调用仍受支持，未弃用。较长名称 class_to_dict 和 update_class_from_dict 也仍受支持。

延迟加载与模块导出#

公共包导出使用 延迟加载 ，使导入顶层包（例如 import isaaclab.sensors ）不会立即引入 pxr 、 omni 或 scipy 等大型依赖。这很关键，因为配置类必须能在 SimulationApp 启动 之前 构建。

我们遵循 SPEC 1：子模块与函数的延迟加载 ，结合 .pyi 类型存根使用 lazy_loader 库（获 NumPy、SciPy、scikit-image、scikit-learn、NetworkX 推荐）。存根是 IDE 自动补全和运行时延迟加载的 唯一权威定义 。

公共导出模块的标准模式：

# mypackage/__init__.py
from isaaclab.utils.module import lazy_export

lazy_export()

旁边放置对应的类型存根：

# mypackage/__init__.pyi
__all__ = ["MyClass", "MyOtherClass", "my_function"]

from .my_module import MyClass, MyOtherClass
from .my_other_module import my_function

.pyi 存根的主要规则：

  • 顶部 __all__ 列表将名称标为公共重新导出项，符合 PEP 484 。

  • 来自同一子模块的导入放在一行；超过 100 字符时，用括号进行多行导入。

  • 本地子模块符号使用 相对导入 （ from .something import ... ）。绝对通配导入（ from pkg import * ）只用于跨包回退，见下文。

  • 包含标准 Isaac Lab 许可文件头。

跨包回退 ：对于重新导出其他包名称的模块，例如委托到 isaaclab.envs.mdp 的任务 MDP 模块，在 .pyi 存根中添加外部包的通配导入：

# isaaclab_tasks/.../mdp/__init__.pyi
__all__ = ["MyReward", "MyObservation"]

from .rewards import MyReward
from .observations import MyObservation

from isaaclab.envs.mdp import *

__init__.py 与标准模式相同，只调用无参数的 lazy_export() ：

# isaaclab_tasks/.../mdp/__init__.py
from isaaclab.utils.module import lazy_export

lazy_export()

运行时， lazy_export 解析 .pyi 存根，并将绝对通配导入 from isaaclab.envs.mdp import * 作为回退：本地子模块中找不到的名称，会到指定包中查找。这也使类型检查器和 IDE 能完整识别重新导出的符号。

相对通配重新导出 ：存根还可使用 from .submodule import * ，立即导出本地子模块的全部公共名称。这在导入时解析，并非延迟加载。仅 API 规模较大或频繁变化，并不足以成为立即导入的理由。

备注

相对通配重新导出绕过延迟加载，在包初始化时立即导入子模块的全部公共名称。一般不建议使用，除非确有必要。优先在存根中列出明确的具名导入，使公共 API 清晰、便于审阅，并保持延迟加载。

# isaaclab_tasks/.../mdp/__init__.pyi
from .rewards import *
from .observations import *

from isaaclab.envs.mdp import *

确保分发 .pyi 存根

在包的 pyproject.toml 中声明存根文件，将它们包含在分发包中：

[tool.setuptools.package-data]
"*" = ["*.pyi"]

提供延迟导出存根的包应保留此配置。pre-commit 的 insert-license 钩子已配置为自动给 .pyi 文件添加许可头（ \.(pyi?|ya?ml)$ ）。

可解析字符串#

配置字段需要引用依赖仿真器运行时的类或可调用对象时，存为 ResolvableString ，而非直接引用。这样可避免构建配置时立即导入 omni 、 pxr 等大型模块。调用或访问需要实现的属性时会触发解析，调用方必须先初始化所需运行时。解析本身不会等待 SimulationApp ，不依赖 Kit 的工作流也无需启动它。

可使用 {DIR} 简写或完整限定模块路径：

# Good — {DIR} shorthand (resolved to the current package at runtime)
class_type: type[Sensor] | str = "{DIR}.sensor:Sensor"

# Good — fully-qualified path (useful for cross-package references)
class_type: type[Sensor] | str = "isaaclab.sensors.my_sensor.sensor:Sensor"

# Bad — eagerly imports the implementation module
from .sensor import Sensor
class_type: type = Sensor

配置机制将 {DIR} 展开为定义该字段的类所在的包，例如 isaaclab.sensors.my_sensor ，而不导入被引用实现。同一包内的引用优先使用 {DIR} ，因为重命名和移动后仍能保持正确。

类型注解 type[Sensor] 所需类，应在 TYPE_CHECKING 条件下导入，使 IDE 仍能补全，而不触发运行时导入：

from __future__ import annotations
import typing

if typing.TYPE_CHECKING:
    from .sensor import Sensor

分开配置与实现文件#

具有配置类的组件，应将配置与运行时实现放在不同文件，使导入配置不会加载大型运行时依赖。这一模式并不要求为无状态函数引入类或配置对象：

my_sensor/
├── __init__.py          # lazy_export()
├── __init__.pyi         # re-exports: SensorCfg, Sensor
├── sensor_cfg.py        # pure data — no runtime deps
└── sensor.py            # implementation — may import omni, pxr, etc.

__init__.py ：通过 lazy_export() 延迟加载存根中的名称：

# my_sensor/__init__.py
from isaaclab.utils.module import lazy_export

lazy_export()

__init__.pyi ：声明供 IDE 补全和延迟加载使用的公共 API：

# my_sensor/__init__.pyi
__all__ = ["SensorCfg", "Sensor"]

from .sensor_cfg import SensorCfg
from .sensor import Sensor

sensor_cfg.py ：纯数据，通过可解析字符串引用实现类，避免导入：

# my_sensor/sensor_cfg.py
from __future__ import annotations
import typing

from isaaclab.utils import configclass

if typing.TYPE_CHECKING:
    from .sensor import Sensor

@configclass
class SensorCfg:
    class_type: type[Sensor] | str = "{DIR}.sensor:Sensor"

sensor.py ：实现部分，只在需要时导入运行时依赖：

# my_sensor/sensor.py
from pxr import Usd

from .sensor_cfg import SensorCfg

class Sensor:
    def __init__(self, cfg: SensorCfg, stage: Usd.Stage) -> None:
        self.cfg = cfg
        self.stage = stage

类型提示#

函数签名和类属性使用具体类型提示。文档字符串描述含义、单位、形状和约束，不重复已注解类型：

def add(a: int, b: int) -> int:
    """Add two integers.

    Args:
        a: The first operand.
        b: The second operand.

    Returns:
        The sum of the operands.
    """
    return a + b

  • 优先使用 list[str] 、 dict[str, int] 等内置集合类型。

  • 可选值使用 X | None 。

  • 类型需要仅运行时可用的导入时，使用 TYPE_CHECKING 和延迟注解。

  • 无返回值函数标注 -> None ，文档字符串省略不必要的 Returns: 章节。

编写代码文档#

文档应使调用方无需阅读实现，即可使用 API。

  • 先说明行为，再解释约束、默认值和相关失败情况。

  • 说明单位、坐标系、形状，以及输入和返回数据的归属或修改行为。

  • 在相关代码附近，用简短注释解释不明显的设计约束。

  • 小示例有助于说明用法时，可提供示例。避免重复签名或逐项叙述操作。

  • 使用平实语言和主动表达，删除重复及含糊限定词。

  • 行为变化时更新文档，并根据当前实现检查示例。

单元测试#

我们使用 pytest 进行单元测试。在最能体现行为的边界，为每个约定指定一个主要测试负责方，保持覆盖精简、快速。先查看该边界现有覆盖；如果能明确覆盖修改后的行为，优先扩展现有测试。

新增、修改、审阅或精简测试时，采用 test-audit 技能 中的编写门槛和保留标准。它维护判断测试收益是否值得其成本的详细条件。

  • 只有现有覆盖未检验的独立行为、回归、边界或失败情况，才添加测试。格式调整和机械性整理不会自动要求新测试。添加前，明确保护的约定、可能发生的回归，以及现有覆盖为何发现不了。不要只为支持测试而添加生产导出、标志、包装器或注入钩子，应检验实际边界。

  • 测试可观察行为和公共约定。避免依赖私有实现细节的断言，或通过重复生产算法计算期望值。避免无断言的冒烟测试、自我比较，以及由模拟对象或测试夹具直接提供测试声称要验证的行为。

  • 确认回归测试在没有修复时因预期原因失败，修复后通过。在错误所属边界覆盖它；在其他层或后端重复测试，需要有独立风险作为理由。

  • 参数矩阵和仿真夹具应聚焦不同执行路径。整合多余覆盖，不要添加重叠用例或无必要地重建同一场景。如果设备、形状和环境数等维度没有检验不同路径，避免构造它们的笛卡尔积。复用已验证该约定的夹具。

  • 移除或合并覆盖前，明确剩余的验证依据，并证明约定被破坏时它会失败；适用时，对负责该行为的生产实现进行针对性变异。保留独立边界情况，以及独立的 API、物理、后端一致性和打包约定。测试慢或断言看起来相似，本身不能证明重复。

  • 先运行范围最小的相关测试。如果缺少可选依赖，找到对应项目依赖组，用 uv run --extra <extra> python -m pytest ... 重试。以缩短测试时间为目标的修改，应在同一机器测量前后耗时，并将核函数编译与执行时间分开。

Linux 和 Windows 使用同样命令：

# Run a particular test
uv run python -m pytest source/isaaclab/test/utils/test_circular_buffer.py::test_reset

# Run all tests in a particular file
uv run python -m pytest source/isaaclab/test/utils/test_circular_buffer.py

# Run source-package tests through the repository test runner
uv run python tools/run_all_tests.py

# Run tooling tests under tools/
uv run isaaclab --test

这些命令在测试失败时均以非零状态退出，因此调用它们的 shell 或 CI 步骤也会失败。
